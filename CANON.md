# Harness Canon

The durable rulings of this harness with their why, and the live rulebook for its maintenance: components, rules files, settings, and methods live here, while [harness-maintenance.md](.claude/rules/harness-maintenance.md) holds the edit gates and the map that loads this file.

---

## 1. Authoring skills, commands, and agents

- **Multi-exemplar:** read sibling components before writing; base format and structure on the best practice across them, never on one target.
- **Persona and headings:** agents get a terse persona (1–3 sentences covering role, specialty, responsibility) at the top of the body, and no H1. Commands and skills get no persona; an H1 only when a genuine title beyond the bare name.
- **Frontmatter:** `name`, `description`, then `disable-model-invocation` and `argument-hint` when present, `tools` (agent allowlist; omit for all; the gating is load-bearing — a read-only agent carries read-only tools), `origin`; add `part-of` when the component belongs to another (e.g., `plan-reviewer` to `plan-review`). `origin` is `custom` (hand-built here), the source name (ported-from: plugins by plugin name, repos by repo name), or `A + B` (multi-source merge). Quote `description` with `""` only when it contains a colon. `argument-hint` marks required slots with `<>`, optional with `[]`; a complete-sentence question hint stays unbracketed; quote it only when YAML requires (a leading `[` or an inner colon). Model-invoked is the default; user-invoked (`disable-model-invocation: true`) is the user's call per component.
- **Description = the routing surface:** one to three sentences carrying stance, trigger, and the mis-invocation guard, with returns as a phrase at most; never a workflow summary; path specs and behavioral detail live in the body. The mis-invocation guard covers lexical or state ambiguity only; naming other skills or phases is workflow-layer routing. A ceding clause naming a sibling skill ("for X, use Y") is allowed only when the two triggers overlap on the same user phrasing even after both are made task-precise; it never summarizes the sibling. User-invoked components (`disable-model-invocation: true`) drop the trigger and the mis-invocation guard and keep a one-to-two-sentence statement of what it does. A `## When to invoke` body section is an anti-pattern; relocate its load-bearing content into the description.
- **Skill references in bodies:** when the referenced skill's procedure executes inline in the current flow, the reference is an invocation, written `call the Skill tool with "X"` (a one-line gloss may follow the call, never replace it). At a genuine boundary (hand-off, user-choice option, ownership statement, ceding clause, vocabulary or file pointer) a plain mention suffices: the target's description re-routes at the next invocation decision. When the invocation's executor is a subagent, it goes into the dispatch prompt as the subagent's own action.
- **Skills and commands:** a body never names its component's own folder (companion files resolve via the invocation's base directory), so renames break nothing; audit/check components inline their full spec (never repoint, since the referenced file may be the audit target, and spec overlap with CLAUDE.md is deliberate, not drift); per-session artifact templates live in the component body, with durable text holding only trigger + pointer.
- **Locality:** a skill serving many callers never carries one caller's exception; the invoking skill owns its own steps' staffing.
- **Skill anchors are phase-anchored and earned:** a skill owning a mid-flow moment routes by a phase-anchored trunk mention plus its description (tdd: named at the trunk's build step, triggered by its description), never by wiring invocations into upstream skills; the anchor is earned only when the moment is a mid-phase instant the model will not think to invoke on its own; phase-explicit spine steps self-defend through their pipeline position (tdd anchors for most builds, code-review sometimes). Routing is verified at the phase moment itself (the skill is never step one), and never judged from a probe run with --tools "" — that flag strips Skill-tool planning, an environment flaw, not a routing failure.

## 2. Adopting and extracting components

- **Extraction pipeline:** read the source and justify what to take → extract verbatim → remove the source's bad parts → enhance what survives → adapt to this harness's conventions and workflows (leave self-run git/gh mutations as-is; component bodies state the action without naming who runs it, except approval gates, which name the user and stay verbatim; the [CLAUDE.md § Git](CLAUDE.md#git) rules and the PreToolUse hook decide the mechanism) → verify against the sources that nothing useful was lost → final acceptance audit (per [dispatch-protocol.md §4 No self-verification](rules/common/dispatch-protocol.md#4-no-self-verification)). Extraction is not a rewrite; relocate useful content, never drop it silently.
- **Source vetting:** before extracting from a pack that ships scripts, MCP configs, or bootstrap logic, audit its executable surface for unexplained network egress, credential-path reads, and instructions hidden in comments or HTML. Reads can execute; git drivers and hooks fire on git operations inside an untrusted checkout, and interpreters import project modules from the cwd. Read packs with the file tools only; never run git or an interpreter inside a pack's checkout.
- **Layer check before "covered":** vocabulary coverage (a checklist names the behavior) is not stance coverage (a bar weighs the behavior); a "covered elsewhere" verdict that only matched vocabulary leaves the stance with no seat.
- **Tone is pressure for a rule:** when a source carries an aggressive stance, extract the rule the tone enforces, in rule form; the tone itself drops.
- **Upstream-review method (adoption falsification):** per hunk — premise-fit (no conflict with the target's own premise or red lines), purpose-translation (the discipline serves the same purpose in the new seat), real-need (the need-moment exists in this harness's workflows), inferable-remainder (non-inferable behavior survives mapping against seated content); re-check rejections too — a component-level verdict says nothing about its content, and purpose overlap tests partially. Standing guardrails — local descriptions are adjudicated routing surfaces — compare bodies, never re-import an upstream description wholesale; reopen a description only when a body change alters scope, trigger, invocation mode, or the returned contract; deploy-watch stays unadopted; wizard and teach-back stay user-invoked; provenance corrections need historical evidence plus a current-source comparison.

## 3. Reviewing and pruning components

- **Pre-existing components:** change only when an effectiveness case justifies it. Description re-tailoring is justified (it is routing); cosmetic trims are not.
- **Owned components are tailored descendants, not copies:** a drift comparison hunts content deltas only — style deltas are the tailoring itself, never a defect; no blind re-syncing.
- **Description protected classes:** the corpus at floor keeps description content in five protected classes — symptom and match words, mis-invocation guards, genuine-overlap cede clauses, deliverable definitions, dispatch-mode clauses; a trim cuts outside these, never inside.
- **Description-walk bar:** terse unless genuinely needed or sibling overlap exists; the review unit is the skill's own body plus its callees' bodies (callees' callees wait for their own turn); after the clause audit, re-check for a concept written twice and compress second mentions.
- **Description precedents:** a negation guard whose positive trigger already scopes is deletable; a cede clause whose boundary the sibling's body enforces is a second home — cut; under-claims are description bugs too; the user-invoked bar in practice is stance-only, enumeration allowed for /-menu picking; third-person "the user" is the trigger convention, and person never depends on invocation mode — a "you" safe in /-menu text becomes the agent-runs-commands misreading after a mode flip; invocation mode is multi-axis (frequency, flow weight and risk, discovery value, adequacy of the no-skill fallback); descriptions open with an imperative or a noun phrase, first-verb -s normalizes; scope statements use "existing", with "legacy" only as a subset trigger match word; no synonym rotation between description and body — named theory stays named. Forgetting-fear asymmetry — high-frequency skills suit user-invoked; low-frequency skills need the listing as their discovery mechanism.
- **Keep/drop:** judge components by purpose and workflow fit. Overlapping components merge, never accumulate. Every add, drop, or rename syncs [README § Skill Sources](README.md#skill-sources) in the same commit.
- **Component form:** a component is lean instruction producing rich output. No knowledge-database skills. Default to a single SKILL.md. A companion file (references, templates) earns its place only when the content genuinely doesn't fit, and a script only when the work can't be carried by instructions alone. An attention checklist (what to look at) directs attention the model would otherwise skip; a lookup table mapping a known error to a known fix replaces judgment the model already has and is rejected.

## 4. Rules files and the trunk

- **CLAUDE.md is the trunk:** the home of preferences and instructions for the user's work; harness-work rules live here, not there. Rules files are extensions of CLAUDE.md; neither restates the other. Coding rules are self-contained; they never reference CLAUDE.md (it co-loads on every injection; rules→rules extends pointers stay, since globs differ).
- **Loading scope:** unscoped (loads every session of every project; only when true for every prompt); project-scope (lives in a project's `.claude/rules/` and loads only there); `paths:`-scoped (loads on matching files). Everything not universal takes one of the latter two.
- **Scoped-frontmatter synchronization:** files sharing a glob block change it together or not at all; a taxonomy change sweeps every file carrying the block.
- **File naming:** a folder's namespace-primary rule file is named `index.md` (the folder carries the namespace); specialist files with narrower globs keep their aspect names (`security.md`, `testing.md`).
- **Lesson landing:** harness lessons follow the proposal gate in [CLAUDE.md § Lesson capture](CLAUDE.md#lesson-capture); the accepted rule lands in the owning harness file.
- **Globs declare the need-moment:** a scoped rule's glob states when the rule is needed, derived from the actual use case; token savings are a by-product, never the motive.
- **Glob-deserve test for merges:** every absorbed member must deserve the shared glob, not merely happen to share it. Accepted approximation costs stand (use-* basename false positives, app/ and pages/ over-fire on Angular-style trees, middleware.ts matching non-Next files, web/testing missing Playwright's tests/ default, fastapi.md path globs false-positiving on same-named dirs, no vue/svelte/astro glob — the harness is tuned to the user's React stack); each fix's over-fire risk exceeds its gap's cost.
- **Reinforcement across consumption moments is not duplication:** the same rule recurring where each consumption moment needs it is reinforcement; mention-once (the trunk's rule) governs only within a single consumption moment.

## 5. Permissions and protection layers

- **Security-plugin layer:** the plugin has three layers. The write-time pattern layer injects deterministic warnings when a write matches a dangerous pattern; they are the only deterministic net and stay on. The two LLM review layers stay off via the shared master switch ENABLE_CODE_SECURITY_REVIEW in settings env; the Stop-hook diff review hijacks the turn boundary on findings, and commit-time review is permanently dead because the user runs every commit. If commit-time security review is ever wanted, the route is the Review phase's security-auditor under the user's gate, never the plugin's layers. The un-gated per-prompt baseline capture (subprocess latency, zero tokens) is the accepted residual cost of keeping the pattern layer.
- **Claude Code permission mechanics:** deny > ask > allow, first match regardless of specificity — a catch-all ask defeats every specific allow (defaultMode=default with bypass disabled makes unlisted commands prompt anyway). A deny blocks the call, not the tool; denied tools stay in the injected context, so deny lists save no tokens. Space-star (X *) is the canonical wildcard and also matches the bare command; X* over-matches (ls* catches lsof); an exact entry matches only the exact string. Compound commands evaluate per subcommand with ask/deny contagious across subshells. Redirect targets are checked against Edit/Write rules separately — a Bash allow never approves the target, so read-only allows cannot be hijacked into writes (/dev/null exempt). Read/Edit deny rules extend to Bash file commands (cat/head/tail/tee) and redirect targets; find-with-action flags (-exec/-delete) are never auto-approvable by prefix rules, and write-flag commands with unquoted globs prompt.
- **Three-layer rtk permissions:** every allow entry is three layers — plain (rewrite-miss insurance), rtk middle (the engine's verified output target), proxy (the deliberate raw-output escape). The rtk PreToolUse hook rewrites via updatedInput before permission evaluation, so rules match the rewritten string; rtk proxy is raw-with-tracking and rtk run (raw, untracked) is denied. Ask carries only universal dangerous verbs (rm, curl, wget, winget); stack-specific installs prompt via default mode — the settings file does not enumerate the toolchain. Write paths inside allows are mechanically excluded. Settings load at session start (restart to apply); the user observes prompts (the agent cannot) — allow probes run silent, ask probes are rejected by the user, deny probes auto-fail.
- **rtk rewrite map:** reliably rewritten — ls, git status/log/diff/show, grep (incl. rg → rtk grep), diff, wc, cat/head/tail → rtk read, pytest (all three spellings), vitest, jest, tsc, npm run lint → rtk lint (a semantic swap; rtk's eslint wrapper, not the project script — the proxy form runs the real script), npm run test. Never rewritten (the plain layer is live) — uv run pytest, winget, git blame, git ls-files, npm test, head -n (long flag), tail -f/-c. `rtk hook check <cmd>` dry-runs the engine. CC-Switch rewrites settings.json one-entry-per-line (compact multi-entry layouts do not survive it).

## 6. Probing

- **Probe method:** a no-file-read headless probe is the natural no-rules baseline for whether a rule is needed: unprompted-produced means inferable means deletable, missed means teeth means keep; silence never proves capability (version pins stay). To test whether a rule fires, seed a task simulation with non-canonical vocabulary and watch the behavior; asking "did rule X apply?" invites confabulated agreement. A behavior-affecting trim is verified by running the same task headlessly before and after it, never judged from the diff alone; probes test removal drift, never an addition's value. Rules entries class by the same probe: good non-default (keep), good but model-default (trim), worse than default (drop); preference pins judge on consistency, never truth.
- **Probe instruments:** fresh `claude -p` processes only — subagent contexts inherit the session-start snapshot, so mid-session edits never propagate into a probe. Delete first, probe after; PASS/FAIL pre-registered before the run; a control is mandatory; grade in main context, never by the subject; empty stdout with exit 0 is INVALID, re-run once; every claim carries its n=1 caveat; prompts in English (the drift condition is Chinese-reply pressure, never a Chinese prompt); security-critical passes don't trim on n=1. stream-json --verbose captures events (the session-JSONL grading path holds no probe transcripts); invocations verify by grepping the session JSONL; a prompt referencing an absent file gets refused under --tools ""; the secret-path hook can match the prompt's own wording.
- **Loading probes:** verify a rule actually loads after a scoping change. Two headless probes — a context check (`claude -p 'Is a rule titled "<TITLE>" in your context? yes/no' --tools ""`, unscoped answers yes) and a load check (rerun with tools enabled, reading a matching file first; scoped answers no before, yes after the read). Probe only novel syntax shapes (character classes, braces, negation, path patterns). A failed probe stops the batch — report before proceeding.
